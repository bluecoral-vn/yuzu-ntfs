# Yuzu NTFS v0.1 Beta — Design

Date: 2026-10-24. Status: **Draft — awaiting owner approval.**
Source: owner request 2026-10-24 ("standalone NTFS app for macOS, best possible performance, independent of Yuzu Drag, first version v0.1 beta"), owner decision **A** (open-source, GPL engine), market research of 2026-10-24 (§9).

Decisions are numbered D1…Dn. Each is tagged **[owner]** (owner said it) or **[designer]** (designer's call, owner may overturn).

## 1. Intent

Plug a Windows NTFS disk into a Mac and use it in Finder read *and* write, at the disk's own speed, with the Mac's security left at Full Security — no kernel extension, no macFUSE, no reboot, no Recovery Mode. When writing would risk the user's data (Windows hibernated it, Fast Startup left it open, the journal is dirty, it is BitLocker-encrypted), the disk mounts read-only and the app says exactly why and what to do.

Why it can exist now: Apple's FSKit (user-space file system app extensions, macOS 15.4+) plus **kernel-offloaded I/O** (the extension hands the kernel extent maps; the kernel moves file data directly) removes both historic trade-offs — kexts (fast, but Reduced Security on Apple Silicon, break on macOS updates) and FUSE (safe, but slow).

### Goals
- G1. Read/write NTFS volumes in Finder and Terminal, auto-mounted on plug-in.
- G2. Performance at or near the device and Apple's own drivers (targets in §6; they are release gates, not aspirations).
- G3. Data safety first: a volume is mounted read/write only when it is provably clean; otherwise read-only with a stated reason.
- G4. Windows interoperability: what Yuzu NTFS writes, Windows `chkdsk` accepts with zero errors, and Windows sees the same names, links, streams and timestamps.
- G5. A small native menu-bar app that shows every NTFS volume, its mode (read/write or read-only + reason) and the one action that helps.

### Non-goals (v0.1)
- Formatting a disk as NTFS (exFAT is the right choice for a blank disk). Maybe later.
- `$LogFile` journal replay / crash repair (v0.2 candidate). v0.1 detects a dirty journal and refuses to write.
- Structural repair (`chkdsk`'s job).
- Creating compressed files; writing to EFS-encrypted files; BitLocker unlock; dynamic disks (LDM); Storage Spaces.
- Mac App Store distribution (impossible under GPL — D2).
- Intel Macs (D5).
- TRIM (FSKit exposes no way to issue it).

### Anti-goals (would be failure even if "it works")
- Corrupting a volume, or silently making Windows run `chkdsk` on it after a clean eject.
- Silently resetting/clearing a dirty journal or deleting `hiberfil.sys` to force read/write (what some drivers do).
- Requiring Reduced Security, a kext, macFUSE, or a reboot.
- Leaving `._*` AppleDouble litter on the user's disk.
- Telemetry, accounts, background daemons.

## 3. User-visible behaviour

### 3.1 First run
1. User drags `Yuzu NTFS.app` to Applications and opens it. Menu-bar icon appears.
2. Onboarding window: (a) beta acknowledgement (D8); (b) enable the file-system extension. On macOS 27 use `FSClient.openFileSystemExtensionsSettings()`; on macOS 26 the System Settings toggle is reported (TT NTFS Native) not to work for third-party modules — P0 determines the working enablement path and onboarding uses it; (c) "Done — plug in an NTFS disk".
3. If the extension is not enabled, the menu shows a persistent "Extension not enabled — Fix" item.

### 3.2 Plug-in
- An NTFS partition (GPT Basic Data / MBR 0x07 with `NTFS    ` OEM id) auto-mounts at `/Volumes/<NTFS label>` through Yuzu NTFS, not Apple's read-only driver (P0 must prove this — risk R2).
- Clean → read/write. Unsafe → read-only + reason (D9) + macOS notification once per plug-in.
- Menu bar lists each NTFS volume: name, size/free, mode badge (RW / RO), reason line when RO, actions: Open, Eject, "Always mount read-only" toggle, "Why read-only?" (explanation sheet).

### 3.3 Eject / sleep / unplug
- Eject (Finder, menu, `diskutil`) flushes all dirty metadata and data, clears the volume dirty flag, then unmounts. A volume ejected cleanly must not trigger `chkdsk` on Windows.
- Sleep: flush before sleep is acknowledged.
- Surprise removal: no hang of Finder or any process; the extension tears down; the next plug-in sees the dirty flag and mounts read-only (D9) — Windows `chkdsk` fixes it.

### 3.4 Files and names (Windows interop)
- Case-insensitive, case-preserving lookup via the volume's `$UpCase` table. Names stored as given (normalisation-preserving); lookup rules for NFC/NFD in D14.
- Characters illegal on Windows (`" * : < > ? \ |`, trailing space/dot) in Mac-created names are mapped to the Services-for-Macintosh private-use range U+F001–U+F07F (the mapping Windows SMB/SFM and Apple SMB already understand) and mapped back on read. [designer]
- Extended attributes ↔ NTFS alternate data streams; `com.apple.FinderInfo` ↔ `AFP_AfpInfo`, resource fork ↔ `AFP_Resource` (the names Apple's built-in driver and SFM use). No `._*` files.
- Symlinks created on the Mac are NTFS symbolic-link reparse points that open on Windows; Windows symlinks and junctions resolve on the Mac. Hard links supported.
- Ownership: all items owned by the mounting user; NTFS ACLs are preserved, not interpreted, not modified. `chmod` succeeds as a no-op except the read-only bit, which maps to `FILE_ATTRIBUTE_READONLY`; hidden flag ↔ `FILE_ATTRIBUTE_HIDDEN`.
- Timestamps: creation, modification, change (MFT change), access — 100 ns NTFS precision round-trips.
- Link target semantics: D15. EFS files: D16. Compressed files: D17.

## 4. Architecture

```
Finder/apps → kernel VFS + UBC ──(file data: kernel-offloaded I/O)──► disk
                     │
                     └─(metadata ops)──► YuzuNTFS.appex (FSKit, sandboxed)
                                          ├─ FSKit layer (Swift): Volume/Item/Handlers
                                          ├─ C bridge: one narrow C ABI
                                          └─ Engine (C, ported fs/ntfs) + platform shim
                                               └─ block I/O via FSBlockDeviceResource
YuzuNTFS.app (menu bar) ◄── status (App Group container + Darwin notifications) ──► appex
```

### 4.1 Components and boundaries
- **Engine (`NTFSCore`)** — ported NTFS code, as close to upstream as possible; upstream sources kept pristine in `upstream/` and our modifications as reviewable diffs. Knows nothing about FSKit.
- **Platform shim (`NTFSPlatform`)** — user-space implementations of the kernel APIs the engine uses (memory, locks, page/folio cache shims, bio → block I/O callbacks, time, errno). Block I/O goes through function pointers supplied by the bridge so tests can run on image files.
- **Bridge (`NTFSBridge`)** — the only C ABI the Swift layer sees: mount/unmount, lookup, getattr/setattr, readdir with attributes, create/unlink/rename/link/symlink, xattr, read/write (non-offloaded path), `blockmap(item, offset, length, flags) → extents`, `complete_io`, statfs, sync, volume state probe (clean / hibernated / fast-startup / dirty-log / dirty-flag / bitlocker / unsupported).
- **FSKit layer (`YuzuNTFSModule`)** — `UnaryFileSystemExtension`, `FSUnaryFileSystem` (probe/load/unload), `FSVolume` subclass, `FSItem` subclass. Exactly **one live `FSItem` per MFT reference** (FSKit tracks items by identity; duplicates silently defer unlinks). Uses `tryReclaim` on macOS 27.
- **App (`YuzuNTFS`)** — menu bar, onboarding, settings, diagnostics export, Sparkle. Reads volume status written by the extension to the shared App Group container; never touches the disk itself.

### 4.2 Performance design (what makes G2 achievable)
1. **Kernel-offloaded I/O** (`blockmapFile` / `completeIO`; `KernelOffloadedIOHandler` on 27) for non-resident, uncompressed, unencrypted `$DATA`. File data never crosses into user space. Resident, compressed and encrypted files carry `inhibitKernelOffloadedIO` and use the read/write handler. Known hazard: advertising offloaded I/O while inhibiting *every* item wedges kernel writeback — the volume must always have a real offloaded path.
2. **Per-file runlist cache** in memory so `blockmapFile` answers without disk reads; reply with as many extents as the packer accepts per call.
3. **Extent-aware cluster allocator**: in-memory free-extent index built from `$Bitmap` at mount; best-fit contiguous allocation; speculative preallocation for sequentially growing files, trimmed on close. Writes honour `initialized_size` (allocate-without-zeroing, never expose stale disk data).
4. **Metadata through the kernel buffer cache** (`metadataRead/Write/Flush/Purge`) after mount completes (it returns EIO during `activate` — start with plain block reads, switch on first success). Purge engine-primed ranges before the kernel writes the same sectors directly.
5. **Directory enumeration returns attributes in the same pass** (feeds `getattrlistbulk`), with stable cookies and a verifier so Finder's incremental listing works on 100k-entry folders.
6. **Concurrency**: per-inode reader/writer locks + one allocation lock (MFT + `$Bitmap`) inside C. No Swift actor hops on hot paths; Swift concurrency only in the FSKit glue and app.
7. **macOS 27 `DataCacheHandler`**: grant `writeBack` to the non-offloaded path (resident/compressed files) so small-file workloads are cached by the kernel.
8. **Correct capabilities**: case-insensitive-preserving, hard links, symlinks, sparse files, 2 TB+ files, fast statfs, persistent object ids (MFT reference), volume UUID derived from the NTFS serial (stable across mounts).

### 4.3 Safety design
- Treat every disk as hostile input: every on-disk structure (boot sector, MFT record + update-sequence fixups, attribute headers, runlists, index nodes, attribute lists, reparse data) is bounds-checked before use; parsers are fuzzed (§7).
- Read/write only after the state probe returns *clean* (D9). The volume dirty flag is set on the first write and cleared on clean unmount.
- Write ordering: data before the metadata that references it; MFT mirror (`$MFTMirr`) kept in sync; `fsync`/`F_FULLFSYNC` flush both the engine's dirty state and the device.
- The engine keeps upstream's `$LogFile` handling for clean volumes; the P0 audit documents exactly what it writes to `$LogFile` on mount/unmount and confirms Windows accepts it.
- Durability contract: D13. The power-cut harness verifies it, not just repairability.

## 5. Delivery phases and gates

Each phase ends with a go/no-go gate. A failed gate stops the next phase.

### 5.1 P0 — Platform spike + engine selection (throwaway code)
Prove, on macOS 26 and macOS 27 Apple Silicon:
- R1 a third-party FSKit module can be enabled by a normal user (find the working path; measure clicks);
- R2 an NTFS disk auto-mounts through Yuzu NTFS rather than Apple's built-in driver;
- R3 kernel-offloaded reads and writes reach ≥ 90 % of raw device sequential throughput on the reference SSD;
- engine selection: build E1 and E2 behind the bridge ABI; pick by (in order) correctness on the fixture set, Windows `chkdsk` result after the write torture subset, sequential and small-file throughput, size of our diff vs upstream, licence/attribution clarity.
**Gate:** R1–R3 proven; engine chosen and recorded as a decision in this document.

### 5.2 P1 — Read path complete
Boot sector/MFT/fixups, attribute lists, `$I30` index, runlists, resident/non-resident, sparse, LZNT1 read, ADS → xattr, reparse (symlink/junction), `$UpCase`, names, timestamps, statfs, offloaded reads.
**Gate:** byte-identical reads vs ntfsprogs/Windows ground truth across the whole fixture set (EFS fixtures: `EACCES` per D16); read targets in §6 met.

### 5.3 P2 — Write path
create, write, truncate, rename (incl. cross-directory, replace), unlink (incl. open-unlinked), mkdir/rmdir, hard link, symlink, xattr set/remove, setattr (times, read-only, hidden), MFT record allocation incl. attribute-list growth, index node split/merge, allocator, offloaded writes, dirty flag, flush on eject/sleep.
**Gate:** torture suite then Windows `chkdsk /scan` → 0 errors; `fsx` N ≥ 1 000 000 ops, 0 mismatches; write targets in §6 met.

### 5.4 P3 — Safety
State probe (hibernate, Fast Startup, dirty log, dirty flag, BitLocker, version), read-only fallback + reasons, power-cut harness, fuzzing.
**Gate:** 100 % of unsafe fixtures mount read-only with the correct reason; every power-cut replay leaves a volume Windows mounts and `chkdsk` repairs, and every file/entry covered by D13 is byte-identical to the pre-cut reference; fuzzers run 24 h per parser with no crash.

### 5.5 P4 — App
Menu bar, onboarding, per-volume status/actions, notifications, settings (per-volume read-only, launch at login), diagnostics export, About with "Beta", EN + VI.
**Gate:** owner walkthrough on a real disk: plug → RW → copy → eject → Windows opens it cleanly; and a hibernated disk → RO + correct explanation.

### 5.6 P5 — Performance pass
Automated benchmark harness (§6), Instruments + `os_signpost` traces, allocator/extent tuning, `DataCacheHandler` on macOS 27.
**Gate:** every §6 target met on the reference hardware on both macOS 26 and 27.

### 5.7 P6 — Release v0.1 Beta
Signing, notarization, staple, Gatekeeper check, Sparkle beta appcast, release notes (EN/VI) listing known limits, `THIRD_PARTY_NOTICES` + GPL source offer (the repo is the source).
**Gate:** fresh-Mac install test (clean user account, Full Security) passes §3.1–3.3 end to end.

## 6. Performance targets (release gates)

Same disk, same port, same files; median of 5 runs; cold cache (unmount/remount between runs).

| Scenario | Baseline | Gate |
|---|---|---|
| Sequential read, one 4 GiB file | Apple built-in NTFS (read-only) | ≥ 100 % |
| Sequential write, one 4 GiB file | Apple exFAT on the same disk | ≥ 90 % |
| Finder copy of 10 000 × 4 KiB files to disk | Apple exFAT | ≤ 1.5 × time |
| `ls -l` of a 100 000-entry directory | Apple built-in NTFS | ≤ 1.2 × time |
| `rm -rf` of a 100 000-file tree | Apple exFAT | ≤ 1.5 × time |
| Random 4 KiB read (1 GiB file, QD1) | Apple built-in NTFS | ≥ 100 % |
| Extension CPU% and RSS during sequential write | — | recorded, no gate in v0.1 |

Reference hardware: one USB-C NVMe SSD (10 Gb/s enclosure) and one USB 3 HDD; the exact models are recorded with the results.

## 7. Verification strategy
- **Fixtures**: NTFS images generated by Windows (via VM) and by `mkntfs`, covering 512 B and 4Kn sectors, cluster sizes 4 KiB–64 KiB, near-full volumes, fragmented files, attribute lists, 100k-entry directories, CJK/emoji/NFC-vs-NFD names, ADS, hard links, symlinks, junctions, sparse, compressed, EFS, hibernated, Fast-Startup, dirty-log, BitLocker. Large images are generated by script, not committed.
- **Oracle**: Windows `chkdsk /scan` and byte-for-byte read-back on Windows, run in a Windows 11 ARM VM with the image or the physical disk attached.
- **Headless engine tests**: `swift test` on the engine package against image files, also under ASan/UBSan.
- **POSIX semantics**: `fsx`, plus a `pjdfstest`-style suite for rename/unlink/link edge cases, run on a mounted volume.
- **Power-cut harness**: block-I/O shim that drops all writes after the N-th, swept over N for a scripted workload; each resulting image checked by the oracle.
- **Fuzzing**: libFuzzer targets for boot sector, MFT record + fixups, runlist decode, index node, attribute list, reparse buffer.
- **Benchmarks**: scripted §6 harness producing a Markdown table per run.

## 8. Risks
| # | Risk | Mitigation |
|---|---|---|
| R1 | Third-party FSKit enablement is broken/awkward on macOS 26 | P0 proves a working path before anything else |
| R2 | Apple's built-in NTFS wins the automount | P0 proves probe precedence; fallback: app-initiated remount (`mountSingleVolume` on 27 needs the `com.apple.developer.fskit.mount` entitlement) |
| R3 | Offloaded I/O slower than promised / FSKit bugs | P0 measures; macFUSE itself documents FSKit I/O is not yet kext-level for non-offloaded paths — our data path avoids that |
| R4 | Data corruption in beta | D8 acknowledgement, D9 refusals, P2/P3 gates, per-volume read-only toggle |
| R5 | Upstream engine bugs | Track upstream fixes; every bug fixed gets a regression test; report upstream |
| R6 | FSKit API churn (27 deprecated `Operations` in favour of `Handler`) | Thin FSKit layer; `#available` branches tested on both OS versions |

## 9. Market facts this design relies on (checked 2026-10-24)
- Paragon NTFS 18 and Tuxera (2027.01, 2026-10-15) still require a kext → Reduced Security on Apple Silicon.
- iBoysoft NTFS ships a kext mode and an FSKit mode; it is on the Mac App Store.
- TT NTFS Native (GPL-2.0, Linux 7.1 `fs/ntfs` port, macOS 26+, arm64) and NTFSKit (GPL-2.0, libntfs-3g, kernel-offloaded I/O) are free FSKit drivers. Yuzu NTFS differentiates on measured performance gates, Windows-verified safety and app UX, not on "no kext".
- FSKit: kernel-offloaded I/O protocol available since macOS 15.4 (renamed `KernelOffloadedIOHandler` in 27); `DataCacheHandler`, `mountSingleVolume`, `openFileSystemExtensionsSettings`, `tryReclaim` new in 27; no TRIM API.
